01

How transcriber development led to a review framework.

I initially used one plan file to track completed work and future steps in my Classroom Live Transcriber project. Development was frequently interrupted and resumed. My own memory of the full plan and its constraints weakened between sessions, while the implementation route kept changing.

The file mixed information with different roles: historical results to preserve, current state to update, and future steps that were still uncertain but looked like settled instructions. A single progress document was no longer enough to guide the next session.

02

A first split helped handoff, then exposed new problems.

I first separated information mainly by how often it changed. Relatively stable background, requirements, constraints, and environment went in one document; current state, step results, blockers, and future plans went in another. Those records plus the code made it possible for another LLM session to take over implementation or checking.

Handoff improved, but two issues remained. Future steps depended on what had actually completed and what was currently running. Meanwhile, agents repeatedly reported plausible conclusions and completed work that I did not have time to independently recheck.

  • Refine responsibilities, not just update frequency

    I gradually reorganized the records so accepted results, the active task, unresolved blockers, and conditional future directions had distinct meanings. A future plan needed to be revisable when the evidence or current state changed.

  • Research experiments made acceptance more consequential

    I reused and refined the structure across other projects, including research experiments. At that point I needed a defensible basis for accepting outputs within my ability to check them. This made independent verification a central design problem.

03

Put evidence and review between generation and acceptance.

I developed the framework around that need: preserve transferable context, then make acceptance a separate decision. This progression is why my research interests now center on LLM agent reliability and trustworthy AI.

  • Inspect what was actually produced

    Identify the code, experiment result, or other artifact and the checks behind it. A completion report helps locate evidence; it does not decide whether the result can be accepted.

  • Give independent review its own judgment

    A separate agent directly inspects the artifacts and forms an acceptance decision. It must also judge whether the chosen checks are sufficient, and can request more evidence or a different verification path.

  • Keep human decisions and current state explicit

    When evidence is unresolved or a decision needs the owner, pause for human judgment. Record accepted results and invalidate conclusions overturned by new evidence so later sessions can continue from the current decision.

04

Where independent review changed a decision.

Later artifact and release reviews made the framework more precise. These cases show how checking the evidence can change acceptance and how the amount of review follows the task.

  • A PDF that passed self-checks but failed independent review

    The PDF looked correct and passed the coding agent's chosen text extraction check. Another extraction path revealed body paragraphs appearing after the signature. Independent review overturned the acceptance; a renderer repair and multiple extraction checks produced the replacement artifact. This changed my definition of independent review: the reviewer must judge whether the verification is sufficient, and be able to choose another evidence path.

  • An audio-app release tied to its actual package

    For AudioShifter, I concentrated checks around package and release identity: tests, native dependencies, tagged source, checksums, a separate Mac, and downloaded release assets. The review structure followed the concentrated release risks.
