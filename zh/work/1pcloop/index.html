01

把验收方法落实为可运行的系统。

当 AI 生成代码的速度超过人工逐项检查的能力时，我希望知道：哪个版本经过了审查，什么证据支持验收，以及何时需要人介入。我实现这套编程流程，将这些判断落实到执行过程。

系统分别处理验收判断和版本对应关系。审查者依据验收标准检查代码、测试和产物；Python 程序核对结论格式、提交关系和证据身份，使记录的决定对应到经过审查的具体版本。

02

将生成与验收分开。

程序将限定范围的任务交给编程与独立审查两个角色。审查结果可以接受产物、要求修复，或暂停等待人工决定。

  1. 01

    明确当前任务

    审查者读取项目约束与当前状态，给出限定范围的指令、允许的修改和需要提交的证据。

  2. 02

    实现并提交证据

    新的编程会话修改目标项目、运行测试，形成代码提交和可供检查的输出。

  3. 03

    判断结果与验证是否充分

    审查者依据验收标准直接检查代码、测试和产物，可以要求补充验证，或给出修复指令。

  4. 04

    记录验收或暂停

    Python 核对结构化结论与证据身份，再记录获授权的验收结果。证据问题未解决或需要人的判断时，流程暂停。

03

为什么两个角色采用不同的会话生命周期。

审查会话持续保留任务的判断背景，每轮编程则从当前有界指令开始。这样，下一轮实现可以交给新的会话，而不需要继承审查者的完整对话。

  • 保留上下文，也要检查它是否过时

    持续会话可能保留旧假设。我从项目规则、当前状态、Git 与产物重建审查所需的权威输入：进度变化时刷新当前记录，长期要求变化时重建审查会话。会话提供工作背景，仓库记录决定当前任务。

  • 验收结论需要对应具体版本

    分支、提交关系、路径和 SHA-256 检查将结论绑定到经过审查的文件，语义上的验收仍由审查者判断。保留审查会话的同时，也需要维护这套身份检查与刷新规则。

  • 恢复之前，先核对什么已经完成

    检查点保存已完成轮次和状态变更，恢复时核对中断前后的操作，无法解释的变化交由人检查。编程已经完成时，记录发布可以单独恢复。

04

课堂转写器任务中实际发生了什么。

我在自己开发的课堂转写器仓库中运行这套流程，扩展原始音频的语言选择。成功运行之前，首次尝试已经产生代码和测试，却因工具运行权限无法创建所要求的 Git 提交。

  • 完成报告与仓库状态不一致，流程停止

    提交失败后，HEAD 未变化，工作区仍有修改。程序检查因此停止流程。我保留恢复证据、恢复基线，修正执行配置并重新验证后，才再次运行。

  • 审查决定增加一项文档工作

    成功运行的第一轮中，审查者接受实现，并要求补充使用文档，说明转写语言与界面语言的区别、英语专用模型的限制。第二轮完成文档，第三轮确认无需继续修改。

  • 最后检查真实音频转写

    随后我用日语和法语实时音频成功完成转写，进行功能验收。整次运行包含 3 轮循环、7 次智能体调用和 2 次提交；审查结论决定何时完成实现、交给人检查。

05

任务验收与记录完成分别显示。

终端界面分别显示任务是否通过验收、当前进度记录是否更新，以及证据摘要是否完成提交和推送。任务已经通过时，记录仍可能需要保存或发布。

每轮摘要在流程仓库中保存对应版本、产物位置、哈希与检查结果。发布失败后，可以只恢复记录发布，避免重新执行已经完成的编程工作。
